# UC-04 integration boundaries (not built)

Status 2026-10-27: UC-04 runs only against local mocks. This page records where each future integration plugs in and what must stay true.
Nothing below has been implemented, and no integration package is a dependency of this project.

## Rules that hold for every integration
- Business rules stay in `Uc04Service` and its rule modules. They must not import an adapter, an HTTP client or an SDK (enforced by `tests/test_integration_boundaries.py` and TC-39).
- The service receives its collaborators by constructor injection: `Uc04Service(cases=..., it_desk=..., policy=..., audit=..., store=...)`.
- No credentials, endpoints or tenant ids in code (checked by a test). Real settings come from configuration or Key Vault at start-up and must not be required for local tests.
- Every result carries `implementation_mode = LOCAL_SIMULATION`. A production wiring must change that value deliberately; mock and production must never be confused silently.
- A real adapter must raise `AdapterError` (or a subclass) on failure. The service then records `ADAPTER_ERROR`, keeps the stored state, and refuses a blind retry until a person calls `acknowledge_adapter_error`.
- The only external write is `it_service_desk.submit_request`, and only for fully approved items (`ToolGateway`, policy file). Approval, provisioning and spend stay with people (GR-02, GR-19, GR-20).

## Known limits an integrator must plan for
- Approvals, evidence and `as_of_date` are supplied by the caller. The service validates their consistency but cannot authenticate them.
- Ticket status is never polled.
- The service is not thread-safe; the local API serialises requests.
- A single request withdrawn by the parent (as opposed to a whole case) has no defined signal; an item missing from a later payload stays stored and unreported.

## Persistence interfaces (interfaces only; no database implementation exists)
Three optional extension points were extracted from existing behaviour so that a durable implementation can be plugged in later without touching a business rule.
All default to today's in-memory behaviour, and none connects to anything.
- `CaseRepository` (`store.py`): what `Uc04Service` needs from case storage. `CaseStore` is the in-memory reference implementation and is unchanged. The interface adds `version_for(case_id)` and the unit-of-work hooks `begin`, `commit` and `rollback`, which are no-ops in memory. `evaluate` and `acknowledge_adapter_error` call the hooks; `submit_eligible` has no commit points yet.
- `AuditSinkPort` (`ports.py`, `AuditLog(sink=...)`): receives every audit entry plus a per-call context (`actor_id`, `run_id`, `invocation_mode`, and the verified `client_id`). The context exists only inside one entry-point call and is never added to an entry. A sink that raises is not ignored.
- `AgentRunRecorderPort` (`ports.py`, `runs.py`, `DirectEntry`/`OrchestratedEntry(run_recorder=...)`): receives one `AgentRunRecord` for every call that returns a result. Calls that raise are not recorded here (they are in the audit trail).
`Uc04Agent` accepts `store`, `audit_sink` and `run_recorder`. The storage design for the fields the shared database does not cover is pending approval by the integration team.
