### F1 — the audit chain correction (supersedes the first pass)

`verify_chain` asserts `entry.sequence == index` over the **complete log
in append order**, and `verify_audit_integrity` is AUDITOR-only
"because the whole log spans every client". `InMemoryAuditLog.append`
uses `sequence = len(self._entries)` — one **global, contiguous,
zero-based** chain across every client and case.

A per-case chain therefore **reports `SEQUENCE_BREAK` on an intact
log**. My first-pass proposal was wrong, and "add three columns" is not
a complete implementation. Consequences:

- Appends must serialize on one counter.
- **Gaps are violations**, so allocation and insert must commit together
  — see F5.
- On a shared table, "the complete log" must be a well-defined row set.
- Truncation of the tail is undetectable by construction
  (`verify_chain` docstring); that needs an external high-water mark.

**Resolution:** prefer a UC-01-owned `uc01_audit_log` table (option B in
the decision doc) — the chain is then unambiguously "every row in this
table", with no marker column and no cross-use-case serialization.

### F2 — tenant reassignment of an approved form

Verified by extracting the trigger body and counting `NEW.<col>`
comparisons:

```
client_id          NEW refs= 0   <-- NEVER COMPARED
client_site_id     NEW refs= 0   <-- NEVER COMPARED
change_reason      NEW refs= 0   <-- NEVER COMPARED
form_id            NEW refs= 0   <-- NEVER COMPARED
```

An `UPDATE onboarding_forms SET client_id = 'other-tenant'` on an
APPROVED row passes every branch. Salary, candidate identity and
approval evidence move tenants with it. This is a **tenant-isolation
hole in the control that exists to prevent exactly that**.

`form_id` matters too: it is the AES-GCM **AAD**. Changing it makes
`salary_and_terms_encrypted` permanently undecryptable
(`repositories.py` binds `aad=form.form_id`).

**Resolution:** compare `client_id` and `form_id` in *every* branch,
including DRAFT/AWAITING_APPROVAL; add `client_site_id` and
`change_reason` to the APPROVED-row comparisons.

### F3 — `TRUNCATE` bypasses append-only

`audit_log_no_delete` is `BEFORE DELETE ... FOR EACH ROW`. `TRUNCATE`
is not `DELETE` and does not fire row triggers. The whole audit table
can be emptied in one statement. Needs
`BEFORE TRUNCATE ... FOR EACH STATEMENT`. Triggers also do not
constrain a superuser or the table owner, and the `REVOKE` line is
still commented out.

### F4 — RLS as drafted would break all writes

11 `FOR SELECT` policies, zero `FOR INSERT`/`FOR UPDATE`. With RLS
enabled and no permissive write policy, every insert from `uc01_app` is
denied. Separately, the policies read `request.jwt.claims` — a
**PostgREST-set** GUC. Under a direct psycopg connection (D6 option A)
that setting is absent, so `uc01_claim_client_ids()` returns empty and
every policy denies. **The RLS draft and the psycopg option are
mutually incompatible as written.**

### F5 — gapless chain is impossible over PostgREST

`PostgrestClient` issues one statement per call with no transaction
(`client.py` module docstring states this). Allocating `sequence` then
inserting is two round trips; a crash between them leaves a gap, and
F1 makes a gap a permanent verification failure. **The audit log cannot
be implemented correctly over PostgREST.** D4 is therefore gated on D6.

### F6 — pre-case entries

`open_onboarding_case` writes `START_GATE_EVALUATED` and
`DUPLICATE_CHECK_EVALUATED` before a case exists; the model allows
`case_id IS NULL` with `request_id` set. These rows still need chain
positions. A global chain handles them naturally — another argument for
F1's resolution.

### F7 — draft and adapter disagree

Draft declares `idempotency_key ... GENERATED ALWAYS AS (...) STORED`.
Live is a plain nullable column, and `SupabaseHrisRecordRepository`
writes it explicitly. Against the draft schema that INSERT **errors** —
Postgres rejects writes to a generated column. Pick one and align.

**Update 2026-11-04:** "live is a plain nullable column" came from
PostgREST metadata, which cannot show generated columns. Tested directly,
the live column is `GENERATED ALWAYS` (a supplied value fails with
SQLSTATE 428C9, on insert and on update) and is `UNIQUE`
(`uq_hris_sync_idempotency`); the generated value equals
`HrisRecord._derive_idempotency_key`. Aligned on the live column: the
adapter no longer sends `idempotency_key`, and the draft generates it.

### F8 / F14 — `next_employee_no()`

`next_employee_no(p_client_id)` takes the tenant as a parameter with no
authorization check: any principal that can execute it can mint numbers
for **any** client. Safe only while execution is restricted to the
backend role. `REVOKE ... FROM PUBLIC/anon` is present; the
`GRANT ... TO uc01_app` is commented out, so currently nobody can
execute it.

It is also `LANGUAGE sql VOLATILE`, not `SECURITY DEFINER`, so the
caller needs direct `UPDATE` on `employee_number_counters` anyway —
which defeats the point of routing through a function. Consider
`SECURITY DEFINER` + `SET search_path = ''` and revoking direct table
UPDATE from `uc01_app`.

For an unseeded client the `UPDATE` matches no row, `RETURNING` yields
nothing, and the function returns **NULL** — the adapter must treat that
as an error, never as "no number".

**Concurrency is correct:** `UPDATE ... RETURNING` takes a row lock and
returns post-update values; a second caller blocks, then re-reads under
READ COMMITTED. Client isolation is per-row, so different clients do not
contend.

## 3. Atomic persistence: psycopg vs. one SQL function

`open_onboarding_case` touches `audit_log`, `employee_number_counters`,
`cases`, `onboarding_forms` (case_id backfill), `person_records`,
`approvals`, `domain_events_outbox`.

**Option A — restricted direct psycopg connection (recommended).**
One `BEGIN`/`COMMIT`; business logic stays in Python and stays tested by
the existing 740 tests; advisory locks become available for
`execute_hris_write` (which wraps an external HTTP call and cannot sit
inside a transaction); `SELECT … FOR UPDATE` replaces the RPC.
Costs: a connection string and a `uc01_app` role must exist; **RLS must
be redesigned** (F4) because `request.jwt.claims` will not be set; and
pooling must be session-mode `:5432`.

**Option B — one PL/pgSQL `open_onboarding_case()` function.**
Works over PostgREST today (one implicit transaction, so genuinely
atomic); no new credentials. Costs: real business logic — start gate,
duplicate rules, variant flags — migrates into SQL, where it is outside
the Python test suite and duplicated against it; the Python
implementation remains as the in-memory path, so **two implementations
of the same rules** must be kept in step. Debuggability and reviewability
both drop.

**Recommendation: A.** B is defensible as a stopgap only if D6 is
refused outright; in that case keep the function a thin
insert-orchestrator that takes already-decided values as parameters, so
no rule logic moves into SQL.

Regardless of choice: reverse the `approve_form_change` write order
(supersede before insert — the partial unique index is checked per
statement), and keep the DB constraints as the real guard
(`person_records_one_open_case_uq` for the duplicate-case race,
`hris_records_idempotency_uq` for retry safety).

## 4. Encryption key — storage, rotation, recovery

Verified: no secret values in any git-tracked file; both `.env` files
gitignored; `.env.example` placeholders empty; no `print`/logging of
secrets in `src/`; key-format errors never echo the value; `SecretStr`
keeps both secrets out of `repr()`.

**Storage.** 32 random bytes, base64, from Key Vault / Supabase Vault,
injected as `UC01_FIELD_ENCRYPTION_KEY`. Never a column default, a
database setting, or a committed file. The key currently in the root
`.env` is a locally generated development key and **must be replaced**.

**Rotation — not implemented.** The ciphertext carries a version byte
(`_VERSION = b"\x01"`) but `FieldCipher` holds exactly one key, so
backward-compatible decryption does not exist. Required to support it:

1. accept a key **set** (current + previous), keyed by version byte;
2. always encrypt with the current key, attempt decryption with the
   version the ciphertext declares;
3. a re-encryption job over `onboarding_forms`, which must preserve
   `form_id` (it is the AAD — see F2);
4. retire the old key only after the job completes.

**Recovery.** There is none: lose the key and every
`salary_and_terms_encrypted` value is unrecoverable. Escrow is a
business decision. `onboarding_forms` currently has 0 rows, so rotating
now is free; that will not stay true.
