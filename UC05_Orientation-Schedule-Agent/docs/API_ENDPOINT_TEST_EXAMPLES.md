## 1. Project overview

The HR Onboarding Agent is a FastAPI service (`sub_agent.api:app`) built on the shared
`hr_onboarding_common` harness. It exposes these groups of routes:

- **Shared agent routes** (`/healthz`, `/v1/runs`, `/v1/approvals*`) — drive `OnboardingAgent`'s
  LangGraph, which currently implements **one** workflow: drafting a client-templated welcome
  message for HR review.
- **Onboarding registry routes** (`/v1/onboarding/*`) — call `OnboardingToolRegistry` directly
  (the same `ToolGateway` + `Policy` + `HITLInbox` + `AuditLog` enforcement used by the agent),
  covering intake, checklist tasks, scheduling, attendance, buddy assignment, and HR policy Q&A.

Both groups share **one** `AgentContext` (built once at process start), so an approval decision
made through `POST /v1/approvals/{id}/decision` is applied correctly no matter which route created
the proposal.

> **NDA/HR policy acknowledgement and signature tracking is out of scope for this agent** (the
> `/v1/onboarding/*/acknowledgements*` routes, §5.12–5.15 below in older captures, were retired).
> **HR Policies Q&A remains fully active** and shares no code with the retired feature — see §10.

All data is synthetic and in-memory (`MockOnboarding`, `FakeCalendar`, `MockEmailAdapter`,
`MockEmployeeDirectory`). Nothing in this service writes to a real HRMS, calendar, or email
provider — see [§11 Troubleshooting](#11-troubleshooting) and the project `README.md` for the full
list of what remains unconfigured.

### Starting the service

```bash
LLM_MODE=offline uv run python -m uvicorn sub_agent.api:app --reload --port 8000
```

- `LLM_MODE=offline` uses the deterministic `FakeLLM` (no API key needed) — this is also the

- Equivalent form: `uv run uvicorn sub_agent.api:app --reload --port 8000`.
- Swagger UI: `http://localhost:8000/docs`

- Raw schema: `http://localhost:8000/openapi.json`

## 3. API base URL and authentication requirements

**Base URL (local):** `http://localhost:8000`

There is no token-based authentication. Identity is read from plain HTTP headers, trusted as-is —
this is explicitly a placeholder (see `hr_onboarding_common/platform/identity.py` and
`sub_agent/api.py`'s `_actor_and_client`): safe only behind a real identity gateway that has
actually validated the caller, **not implemented here**.

| Header | Required on | Meaning |
|---|---|---|
| `X-User-Id` | every route | Caller identity, e.g. `user:hr-admin-01` or a specific id like `TL-001` when a decision requires a specific approver (see §7, Workflow C) |
| `X-User-Roles` | every route (optional, but needed for gated actions) | Comma-separated roles, e.g. `hr_admin`, `team_lead`, `buddy` |
| `X-Client-Id` | every `/v1/onboarding/*` route only | The caller's authorized tenant/client, e.g. `CLIENT-ACME`. **Not required** on `/v1/runs` or `/v1/approvals*` |

Missing `X-User-Id` or `X-Client-Id` (where required) → `422 Unprocessable Content` (FastAPI's own
header-presence validation, before any application code runs).

### 5.2 `POST /v1/runs`

**Purpose:** run `OnboardingAgent`'s LangGraph — currently: load the employee record, draft a
client-templated welcome message via `services/welcome.py`, and submit it for HR approval.

**Headers:** `X-User-Id` (required), `X-User-Roles` (optional, e.g. `hr_admin`). **No** `X-Client-Id`
— this route is not tenant-scoped at the HTTP layer (tenant correctness here comes from the
employee record's own `client_id`).

**Request body** (`RunBody`):
```json
{
  "instance": "EMP-001",
  "input": {"employee_id": "EMP-001"}
}
```

```bash
curl -s -X POST http://localhost:8000/v1/runs \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user:hr-admin-01" -H "X-User-Roles: hr_admin" \
  -d '{"instance":"EMP-001","input":{"employee_id":"EMP-001"}}'
```

**📝 Illustrative response (200), shape confirmed from `agent.py`/`tool_registry.py`'s
`ActionTaken`/`AgentResponse` contracts:**
```json
{
  "response": {
    "run_id": "run-xxxxxxxxxxxx",
    "status": "acted",
    "proposals": [],
    "actions_taken": [{
      "tool": "welcome.draft_communication",
      "subject_id": "EMP-001",
      "approval_id": "apr-xxxxxxxxxxxx",
      "detail": {
        "draft_id": "comm-xxxxxxxxxxxx",
        "subject": "Welcome to Acme People Team, Sara Al Marzooqi!",
        "body": "Dear Sara Al Marzooqi,\n\nWelcome to Acme People Team! ...",
        "status": "draft"
      }
    }],
    "exceptions": [],
    "provenance": {"...": "agent/model/skill/tool-call metadata"}
  },
  "approvals": []
}
```
**Important fields:** `status` is `"acted"` (not `"proposed"`) because the welcome service already
submits its own HITL item — the real approval id is `actions_taken[0].approval_id`, **not** the
top-level `approvals` list (which stays empty for this action; this is a known, documented
contract quirk — see the project `README.md`). Running this twice for the same employee creates a
**second** draft and a second approval item; there is no dedup at this layer.

**Postman:** `POST` → `/v1/runs`; headers `X-User-Id`, `X-User-Roles`; body as above; expect `200`.

**Validation/error tests:**
| Scenario | How | Expected |
|---|---|---|
| Unknown employee | `"employee_id": "EMP-DOES-NOT-EXIST"` | `200` with `status: "exception"`, `exceptions[0].code: "MISSING_DATA"` (the agent's own contract turns this into a structured exception, not an HTTP error) |
| Missing `X-User-Id` | omit header | `422` |
| Malformed body | `"input": {}` (missing `employee_id`) | `422` |
| Cancelled/withdrawn case | run against an employee whose `case_status` was set to `cancelled`/`withdrawn` | `200` with `status: "exception"`, `exceptions[0].code: "POLICY_BREACH"` (no new route exists to change `case_status` via HTTP yet — this must be set through code/tests) |

### 5.5 `POST /v1/approvals/{approval_id}/decision`

**Purpose:** approve / edit / reject any pending approval, regardless of which route created it.
This is the **only** way any gated write (confirm a booking, assign a buddy, sign off on a comms
draft, resolve an attendance decline) actually takes effect — see §7 for full sequences.

**Request body** (`DecisionBody`):
```json
{
  "decision": "approved",
  "reason_code": null,
  "note": null,
  "edited_payload": null
}
```
- `decision`: one of `approved`, `edited`, `rejected` (never `pending`).
- `reason_code` is **required** for `edited`/`rejected` — one of `tone`, `accuracy`, `missing_info`,
  `bias_language`, `wrong_band`, `not_relevant`, `policy`, `duplicate`, `timing`, `other`.
- `edited_payload` is **required** for `edited` (e.g. `{"new_start": "2026-11-03T09:00:00Z"}` to
  reschedule a declined session — see Workflow in §7).

```bash
curl -s -X POST http://localhost:8000/v1/approvals/apr-xxxxxxxxxxxx/decision \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user:hr-admin-01" -H "X-User-Roles: hr_admin" \
  -d '{"decision":"approved"}'
```

**✅ Verified live (from a prior session; shown as evidence of the real shape, not from this
document's run):**
```json
{"id":"apr-d45ef0bf9132","gate":"comms_approval","approver_role":"hr_admin",
 "workflow":"employee-onboarding","workflow_instance":"EMP-001","agent":"employee-onboarding",
 "proposal_type":"welcome_message","subject_id":"EMP-001","payload":{"...":"..."},
 "status":"approved","approver":"user:hr-admin-01","final_payload":{"...":"..."},
 "decided_at":"2026-10-21T16:42:23.983671Z", "sla_hours":24}
```

**Validation/error tests:**
| Scenario | Expected |
|---|---|
| Unknown `approval_id` | `404` |
| Caller's `X-User-Roles` doesn't include the gate's required role | `403` |
| Approver is not the *specific* `team_lead_id`/`buddy_id` on record (for `team_intro`/`buddy_intro` bookings) | `403` — `scheduling.UnauthorizedApproverError`, even though the HITL item itself gets recorded as decided |
| `rejected`/`edited` without `reason_code` | `422` |
| `edited` without `edited_payload` | `422` |
| Same `approval_id` decided twice | `409` ("already decided") |


### 5.16 `POST /v1/onboarding/{employee_id}/sessions` — Schedule Session

**Purpose:** UC steps 3/4/7 — book orientation/induction/team-intro (not buddy-intro — see 5.18).
Validates office hours (09:00–18:00 **Asia/Dubai**, configurable), weekend days (Fri/Sat by
default), and holidays *before* ever touching the calendar; then checks calendar availability,
books, records per-attendee invitations, and submits a `scheduling_approval` item.

**Request body** (`ScheduleSessionBody`):
```json
{
  "session_type": "orientation",
  "start": "2026-11-02T09:00:00Z",
  "attendees": ["HM-01"]
}
```
`session_type` ∈ `orientation | induction | team_intro | buddy_intro` (but use the dedicated
buddy-intro route for `buddy_intro`). `start` is UTC ISO-8601; `2026-11-02T09:00:00Z` = 13:00
Dubai time, safely inside the 09:00–18:00 window for any of the four durations
(60/90/30/30 minutes respectively).

```bash
curl -s -X POST http://localhost:8000/v1/onboarding/EMP-002/sessions \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user:hr-admin-01" -H "X-User-Roles: hr_admin" -H "X-Client-Id: CLIENT-ACME" \
  -d '{"session_type":"orientation","start":"2026-11-02T09:00:00Z","attendees":["HM-01"]}'
```

**📝 Illustrative response (200)**, shape confirmed from the route handler (`{"session": ..., "approval": ...}`):
```json
{
  "session": {
    "id": "session-xxxxxxxxxxxx", "employee_id": "EMP-002", "client_id": "CLIENT-ACME",
    "session_type": "orientation", "scheduled_start": "2026-11-02T09:00:00Z",
    "scheduled_end": "2026-11-02T10:00:00Z", "status": "scheduled",
    "attendees": ["EMP-002", "HM-01"], "external_event_ref": "evt-xxxxxxxxxxxx"
  },
  "approval": {"id": "apr-xxxxxxxxxxxx", "gate": "scheduling_approval",
              "approver_role": "hr_admin", "subject_id": "EMP-002"}
}
```
`status` is `"scheduled"` (a draft hold), **not** `"confirmed"`, until the approval is decided
(see Workflow in §7). `approver_role` varies by `session_type`: `hr_admin` for
orientation/induction, `team_lead` for team-intro (must be the employee's own `team_lead_id`).

**Validation/error tests:**
| Scenario | How | Expected |
|---|---|---|
| Missing required field | omit `start` | `422` |
| Invalid enum | `"session_type": "not_a_real_type"` | `422` |
| Out-of-office-hours | `"start": "2026-12-07T23:00:00Z"` (03:00 Dubai) | `422` — `InvalidMeetingTimeError` |
| Weekend day | a Friday/Saturday in Dubai time | `422` |
| Double-booking the same attendee/slot | book the same `employee_id`+time twice | `409` — `CalendarConflictError` |
| Calendar provider outage | `"attendees": ["CALENDAR-OUTAGE"]` | `502` — `CalendarBookingError`, nothing created |
| Unknown employee | — | `404` |
| Cross-tenant | — | `403` |

### 5.25 `POST /v1/onboarding/policy-questions` — Policy Question

**Purpose:** UC step 8 — answer an HR policy question using only retrieved, tenant-scoped,
currently-effective policy documents, with section-level citations. Returns a safe "no answer"
(`answer: null`) rather than guessing when evidence is insufficient — **the model is never even
called** when retrieval finds nothing.

**Request body** (`PolicyQuestionBody`):
```json
{"question": "Can I share confidential company information?", "as_of": "2026-11-01", "employee_id": null}
```

```bash
curl -s -X POST http://localhost:8000/v1/onboarding/policy-questions \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user:hr-admin-01" -H "X-User-Roles: hr_admin" -H "X-Client-Id: CLIENT-ACME" \

```

**✅ Verified live response (200):**
```json
{"answer":"Per C1: Employees must not disclose confidential company information to third parties without\nauthorization from their manager and the Legal team.",
 "citations":[{"doc_id":"POL-CONDUCT-001","title":"Employee Conduct Policy","section":"Confidentiality",
```

| Scenario | `question` | Expected |

## 6. Success and error response reference

| HTTP status | Meaning in this service | Raised by |
|---|---|---|
| `200` | Success | — |
| `404` | Record not found | bare `KeyError` (unknown employee/session/ack/draft/client config) |
| `403` | Tenant mismatch, policy violation, or unauthorized approver | `PermissionError` and subclasses (`TenantAuthorizationError`, `TenantMismatchError`, `PolicyViolation`, `UnauthorizedApproverError`) |
| `409` | Duplicate / conflict | `DuplicateRecordError` subclasses, `DuplicateSendError`, `CalendarConflictError`, HITL "already decided" |
| `422` | Validation failure (incl. FastAPI's own request-shape validation) | Pydantic `ValidationError`, `SchedulingError` subclasses (`InvalidMeetingTimeError`, `NoBuddyCandidatesError`, `BuddyNotAssignedError`), `UnknownTemplateError`, `UnsupportedLanguageError`, `IncompleteEmployeeDataError`, `MalformedOfferAcceptanceEmailError` |
| `502` | Upstream (simulated) provider failure | `CalendarBookingError`, `EmailServiceError` |

This mapping is registered explicitly in `api.py` (`app.add_exception_handler(...)`), not guessed —
see that file for the authoritative list.

## 7. End-to-end business workflow tests

All commands assume `ACME` headers:
```bash
ACME=(-H "Content-Type: application/json" -H "X-User-Id: user:hr-admin-01" -H "X-User-Roles: hr_admin" -H "X-Client-Id: CLIENT-ACME")
```
(bash array; on systems without array support, repeat the three `-H` flags inline as shown earlier.)

### Workflow A — Employee onboarding intake

```bash
# 1. Submit intake (complete directory data)
curl -s -X POST http://localhost:8000/v1/onboarding/intake \
  -H "Content-Type: application/json" -H "X-User-Id: user:hr-admin-03" -H "X-User-Roles: hr_admin" \
  -H "X-Client-Id: CLIENT-TEST-A" -d '{"event_id":"EVT-001"}'
# -> 200, employee_id "EMP-TEST-001"

# 2. Duplicate-prevention: replay the same event
curl -s -X POST http://localhost:8000/v1/onboarding/intake \
  -H "Content-Type: application/json" -H "X-User-Id: user:hr-admin-03" -H "X-User-Roles: hr_admin" \
  -H "X-Client-Id: CLIENT-TEST-A" -d '{"event_id":"EVT-001"}'
# -> 200, SAME employee_id, no second case created

# 3. Retrieve the record
curl -s http://localhost:8000/v1/onboarding/EMP-TEST-001 \
  -H "X-User-Id: user:hr-admin-03" -H "X-User-Roles: hr_admin" -H "X-Client-Id: CLIENT-TEST-A"
# -> 200, case_status: "active", buddy_id: null

# 4. Incomplete-data case (expected 422, not a bug)
curl -s -X POST http://localhost:8000/v1/onboarding/intake \
  -H "Content-Type: application/json" -H "X-User-Id: user:hr-admin-03" -H "X-User-Roles: hr_admin" \
  -H "X-Client-Id: CLIENT-TEST-A" -d '{"event_id":"EVT-002"}'
# -> 422, IncompleteEmployeeDataError, no case created for EMP-TEST-003
```

### Workflow B — Onboarding tasks and activities

```bash

curl -s "${ACME[@]}" http://localhost:8000/v1/onboarding/EMP-002/tasks
```

### Workflow C — Buddy assignment and human approval

```bash
# 1. Propose
RESP=$(curl -s -X POST "${ACME[@]}" http://localhost:8000/v1/onboarding/EMP-002/buddy)
echo "$RESP"   # -> {"buddy_id": "EMP-010", "approval": {"id": "apr-...", ...}}

# 2. Capture the approval id (manually, or with jq: APPROVAL_ID=$(echo "$RESP" | jq -r .approval.id))

# 3. Retrieve the approval record
curl -s "${ACME[@]}" http://localhost:8000/v1/approvals/<APPROVAL_ID>

# 4. List pending approvals for this gate
curl -s "${ACME[@]}" "http://localhost:8000/v1/approvals?gate=buddy_assignment&status=pending"

# 5. Approve it
curl -s -X POST "${ACME[@]}" http://localhost:8000/v1/approvals/<APPROVAL_ID>/decision \

curl -s "${ACME[@]}" http://localhost:8000/v1/onboarding/EMP-002
# -> buddy_id: "EMP-010"

#  -- see §11, "remaining gaps")

curl -s -o /dev/null -w "%{http_code}\n" -X POST "${ACME[@]}" \

# -> 409

# 8. Invalid decision: reject without a reason_code -> 422
curl -s -o /dev/null -w "%{http_code}\n" -X POST "${ACME[@]}" \
  http://localhost:8000/v1/approvals/<APPROVAL_ID2>/decision -d '{"decision":"rejected"}'
```

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `422` on every `/v1/onboarding/*` call | Missing `X-Client-Id` header | Add it; it is required on every onboarding route (not on `/v1/runs`/`/v1/approvals*`) |
| `403` on a read/write you expected to succeed | `X-Client-Id` doesn't match the target employee/session's actual `client_id` | Use `CLIENT-ACME` for `EMP-001`/`EMP-002`, `CLIENT-GLOBEX` for `EMP-101` |
| `422 InvalidMeetingTimeError` when scheduling | `start` falls outside 09:00–18:00 **Asia/Dubai**, or on a Friday/Saturday, or on a configured holiday | Convert your desired local time to UTC first (Dubai is UTC+4, no DST) |
| `422 BuddyNotAssignedError` on buddy-intro scheduling | No buddy approved yet for that employee | Run Workflow C first |
| Repeated `409 CalendarConflictError` across test runs | The in-memory calendar is a **process-lifetime singleton** — the same employee/attendee/time slot booked in an earlier test run is still "busy" until the server restarts | Use a fresh employee id and/or a different `start` time per test, or restart the service |
| `Connection refused` on `localhost:8000` | Service not running, or a previous instance still holds the port | Check with `curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8000/healthz`; on Windows, find and stop the stale process via `Get-NetTCPConnection -LocalPort 8000` |
| Want to see a failed invitation | No seed data currently produces one via HTTP | Use `FakeCalendar(invite_failures={...})` in a test, or extend the seed data — this is a code-level fixture, not configurable via the API |
| `LLM_MODE=live` requires a real key | You switched off the default offline mode | Set `ANTHROPIC_API_KEY` as a local environment variable only; never commit it or put it in this document |

**What this service does *not* do (by design, not a bug):** send real emails, create real calendar
events, or call a real HRMS/Teams/Outlook API. Every "send" or "book" action in this document is
against an in-memory fake. NDA/HR policy acknowledgement and signature tracking is not a
responsibility of this agent at all (see §1). See the project `README.md`'s "Known limitations" /
"Production deployment prerequisites" sections for the authoritative list.
